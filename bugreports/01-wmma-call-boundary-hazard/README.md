# [AMDGPU] WMMA read-after-write hazard is not handled across a call boundary (gfx11, gfx12): wrong results

Suggested labels: `backend:AMDGPU`, `miscompilation`.
Status: local draft, not filed upstream.

## Summary

A WMMA/SWMMAC instruction whose result is the A or B operand of the next WMMA/SWMMAC needs at least one other VALU
instruction between the two (a `v_nop` is enough). The compiler inserts it when both WMMAs are in one function
(see `control_inline` in `repro.hip`: `v_wmma ... ; v_nop ; v_wmma`).

When the first WMMA is the last instruction of a non-inlined function that returns the result untouched, and the
caller's next instruction after the call is a WMMA that reads that result as A, no `v_nop` is emitted on either side
of the call:

```
callee:   v_wmma_f16_16x16x16_f16 v[0:3], v[4:7], v[8:11], v[0:3]
          s_setpc_b64 s[30:31]
caller:   s_swappc_b64 s[30:31], s[0:1]
          v_wmma_f32_16x16x16_f16 v[12:19], v[0:3], v[20:23], v[12:19]
```

On a Radeon RX 9070 XT (gfx1201) this gives wrong results (64 of 256 outputs), bit-identical to what the forbidden
hand-written sequence without `v_nop` gives; with a `v_nop` the same inputs are right. The same gap exists on gfx11
(RX 7900 XT, gfx1100: 44 of 256 wrong). Plain C++ triggers it: no inline assembly is needed, only a callee that is not
inlined and ends in a matrix instruction.

All compilers tried emit the same gap: ROCm 10.1 and 10.2 (AMD clang 24.0.0git, two different commits) and upstream
Fedora clang 22.1.8, for gfx1201, gfx1200, gfx1151 and gfx1150.

## Reproducer

`repro.hip` (excerpt; the file has no dependencies beyond `hip/hip_runtime.h`):

```cpp
__device__ __attribute__((noinline)) v8h first_mm(v8h c, v8h a, v8h b) {
    return __builtin_amdgcn_wmma_f16_16x16x16_f16_w32_gfx12(a, b, c);
}
__global__ void caller_plain(const v8h *A, const v8h *B, const v8h *C16, const v8h *B2, const v8f *C2, v8f *D) {
    const int l = __builtin_amdgcn_workitem_id_x();
    const v8h b2 = B2[l];
    const v8f c2 = C2[l];
    const v8h d1 = first_mm(C16[l], A[l], B[l]);
    D[l] = __builtin_amdgcn_wmma_f32_16x16x16_f16_w32_gfx12(d1, b2, c2);
}
```

Commands (device code only, no GPU needed). `<rocm>` is a ROCm install root:

```
<rocm>/bin/hipcc -x hip --cuda-device-only -S -O3 --offload-arch=gfx1201 repro.hip -o repro.s
/usr/bin/clang++ --rocm-path=<rocm> -nogpulib -x hip --cuda-device-only -S -O3 --offload-arch=gfx1201 repro.hip -o repro.s
<rocm>/bin/hipcc -x hip --cuda-device-only -S -O3 --offload-arch=gfx1151 repro_gfx11.hip -o repro_gfx11.s
```

The kernels use `__builtin_amdgcn_workitem_id_x()` instead of `threadIdx.x`, so `-nogpulib` builds have no external
device-library call that would put an unrelated VALU between the call and the WMMA.

Expected (what the hardware rule requires): a `v_nop` (or other VALU instruction) between the callee's WMMA and the
caller's next WMMA, for example before `s_setpc_b64`.

Actual: none (listings below, from `verify_cpu.sh` outputs).

ROCm 10.1, gfx1201, -O3 (identical for ROCm 10.2 -O3 and -O1, and for Fedora clang 22.1.8):

## Hardware evidence

Measured with the study's equivalent kernels (`first_mm_tied` called from `h_call4`; same listing shape and register
numbers as `repro.hip`). The kernels in this bundle were not run on a GPU; this batch was CPU only. Inputs are small
integers, so the CPU model is exact. Control sequences are inline assembly with and without the `v_nop`.

| GPU | Compiler / opt | Plain C++ call shape | Inline asm with `v_nop` | Inline asm without `v_nop` | Compiler's own straight-line chain |
|---|---|---|---|---|---|
| RX 9070 XT (gfx1201) | ROCm 10.1 -O3 | 64 of 256 wrong, two committed runs, bit-identical to the no-`v_nop` asm | 0 of 256 | 64 of 256 | 0 of 256 |
| RX 9070 XT (gfx1201) | ROCm 10.1 -O1, -O2, -Os | 64 of 256 wrong | 0 of 256 | 64 of 256 | 0 of 256 |
| RX 9070 XT (gfx1201) | ROCm 10.2 -O3 and -O1 | 64 of 256 wrong; 0 of 256 differ from the no-`v_nop` asm | 0 of 256 | 64 of 256 | 0 of 256 |
| RX 7900 XT (gfx1100) | ROCm 10.1 -O3 and -O1, ROCm 10.2 -O3, system clang 20.0.0.rocm (ROCm 7.1.1) -O3 | 44 of 256 wrong in every launch (8 launches x 3 jobs per build); equal to the no-`v_nop` asm on an extra launch per job | 0 of 256 | 44 of 256 | 0 of 256 |

Notes:
- At -O0 the two WMMAs are 51 or more instructions apart (loads and stores to the stack between them), so no wait is
  needed there and the gap does not matter; -O0 does not test the hazard recognizer.
- On gfx1201, the ROCm 10.1 hardware runs used LACT profile "Testing" (stock core clock and voltage, 1258 MHz memory,
  317 W cap with a 1.2x regulator mod), and the 2026-11-26 ROCm 10.2 follow-up used the overclocked profile (+150 MHz
  core, -50 mV, 1409 MHz memory request, 374 W cap with the 1.2x mod). The wrong-result counts do not depend on the
  clock.
- gfx1150/gfx1151: listings only. No such card was available.
- For gfx1100 one variant that orders the other operands with an empty asm gave 0, 0, then 44 in the launches of one
  ROCm 10.1 -O3 job and 44 in all other launches; the plain C++ shape gave 44 every time.

## Workaround

Keep the matrix chain in one function (`__forceinline__` / `always_inline`), or tie a `v_nop` to the returned value so
it lands between the call and the next WMMA:

```cpp
v8h d1 = first_mm(C16[l], A[l], B[l]);
asm volatile("v_nop" : "+v"(d1));
D[l] = WMMA_F32(d1, b2, c2);
```

`workaround_asm_nop` in `repro.hip` shows `s_swappc_b64 ; v_nop ; v_wmma` in every listing of the matrix above. The
workaround was checked at listing level only, not on hardware.

## Suggested fix direction

The recognizer that fixes the in-function case has no state at a function boundary (INFERRED from the listings; the
LLVM source was not read for this report). Either of these would close the gap; the choice is the maintainers':
1. In a callee, treat the function exit (`S_SETPC_B64` return) as a use: if the last vector instruction before the
   return is a WMMA/SWMMAC, insert a `v_nop` before the return.
2. In a caller, after a call (`s_swappc_b64`), insert a `v_nop` if the next vector instruction is a WMMA/SWMMAC.

Both cost one VALU slot at a call that already costs dozens. `test_wmma_call_hazard.ll` has a `FIXED` prefix for
option 1; any VALU instruction on either side of the call also satisfies the hazard.

## Run the checks locally (CPU only)

```
bash verify_cpu.sh [--out DIR]
```

It builds every cell of the matrix, scans the listings, compiles the IR test, runs `FileCheck` when it is installed
and runs the deliberate breaks. Overrides: `ROCM_101`, `ROCM_102`, `FEDORA_CXX`, `FEDORA_CLANG`.

Deliberate breaks (a break must turn the detector RED, the untouched listing must be GREEN). Last run:

- original listing: bug_present=yes (GREEN means the bug is detected)
- break 1, V_NOP inserted before s_setpc_b64 in the callee: bug_present=no (RED expected)
- break 2, V_NOP inserted after s_swappc_b64 in the caller: bug_present=no (RED expected)
- restored original: bug_present=yes (GREEN expected)
- IR output with a V_NOP inserted: FileCheck FIXED passes (as expected after a fix)
- IR output with a V_NOP inserted: FileCheck CURRENT fails (RED, as expected)
