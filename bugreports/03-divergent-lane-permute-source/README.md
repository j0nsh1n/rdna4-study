# [AMDGPU] llvm.amdgcn.permlane16/permlanex16 with fetch-inactive: the source computation is sunk into the divergent region, inactive partner lanes supply stale values (gfx12)

Suggested labels: `backend:AMDGPU`, `miscompilation`.
Status: local draft, not filed upstream.

## Summary

`__builtin_amdgcn_permlane16` and `__builtin_amdgcn_permlanex16` take a fetch-inactive flag. With it set, the
instruction reads its source VGPR from lanes that are switched off in EXEC (confirmed on a gfx1201 card). So

```cpp
const unsigned v = X[l] * 3u + 1u;               // every lane computes v
unsigned y = 0xDEAD0000u + l;
if (l < n) y = __builtin_amdgcn_permlane16(y, v, sel0, sel1, /*fetch_inactive=*/true, false);
```

should hand an active lane its partner's `v` even when the partner failed `l < n`. The compiler sinks the load and the
arithmetic that produce `v` into the branch, because the permute is the only user. A switched-off partner never
executes them, so the register the permute reads from it still holds an earlier value. The active lane receives that
stale value.

On a Radeon RX 9070 XT, every active lane whose partner is switched off gets the stale value (100 % of those lanes,
for 3 of the 5 mask shapes tried per permute). With the source pinned in front of the branch (empty `asm volatile` on
`v`) the same lanes are 100 % right.

The sinking happens in the IR passes (`opt -passes=sink` and `-passes=instcombine` both do it on the IR reproducer),
not in the backend's MachineSink: `-mllvm -disable-machine-sink` leaves the result unchanged.

All compilers tried behave the same: ROCm 10.1, ROCm 10.2 (AMD clang 24.0.0git, two commits) and upstream Fedora clang
22.1.8, gfx1201 and gfx1200.

## Reproducer

`repro.hip` (excerpt):

```cpp
__global__ void bad_sunk(const unsigned *X, unsigned *Y, int n) {
    const int l = __builtin_amdgcn_workitem_id_x();
    const unsigned v = X[l] * 3u + 1u;
    unsigned y = 0xDEAD0000u + l;
    if (l < n) {
        y = __builtin_amdgcn_permlane16(y, v, 0x89ABCDEFu, 0x01234567u, true, false);
    }
    Y[l] = y;
}
__global__ void good_pinned(const unsigned *X, unsigned *Y, int n) {
    const int l = __builtin_amdgcn_workitem_id_x();
    unsigned v = X[l] * 3u + 1u;
    asm volatile("" : "+v"(v));                  // v is defined by every lane, in front of the branch
    unsigned y = 0xDEAD0000u + l;
    if (l < n) {
        y = __builtin_amdgcn_permlane16(y, v, 0x89ABCDEFu, 0x01234567u, true, false);
    }
    Y[l] = y;
}
```

Commands (device code only, no GPU needed). `<rocm>` is a ROCm install root:

```
<rocm>/bin/hipcc -x hip --cuda-device-only -S -O3 --offload-arch=gfx1201 repro.hip -o repro.s
/usr/bin/clang++ --rocm-path=<rocm> -nogpulib -x hip --cuda-device-only -S -O3 --offload-arch=gfx1201 repro.hip -o repro.s
```

Actual (ROCm 10.1, gfx1201, -O3). In `bad_sunk` the load and the multiply-add that define `v1` are after the mask write,
and the permute reads `v1` (the register that also holds the initial `y`):

```
	v_or_b32_e32 v1, 0xdead0000, v0
	...
	s_and_saveexec_b32 s4, vcc_lo
	s_cbranch_execz .LBB0_2
; %bb.1:
	global_load_b32 v1, v0, s[0:1]
	s_mov_b32 s0, 0x89abcdef
	s_wait_loadcnt 0x0
	v_mad_co_u64_u32 v[1:2], null, v1, 3, 1
	s_delay_alu instid0(VALU_DEP_1)
	v_permlane16_b32 v1, v1, s0, 0x1234567 op_sel:[1,0]
```

In `good_pinned` the same instructions are in front of `s_and_saveexec_b32`:

```
	global_load_b32 v1, v3, s[4:5]
	...
	v_mad_co_u64_u32 v[1:2], null, v1, 3, 1
	v_or_b32_e32 v2, 0xdead0000, v0
	;;#ASMSTART
	;;#ASMEND
	s_and_saveexec_b32 s0, vcc_lo
	...
	v_permlane16_b32 v2, v1, s1, 0x1234567 op_sel:[1,0]
```

Expected: the definition of `v` stays in front of the branch (as `good_pinned` shows it can), or the compiler does not
move a value that feeds a cross-lane read into a region that not every lane executes.

## Hardware evidence (RX 9070 XT, gfx1201)

Measured with the study's equivalent kernel `w_perm` (ROCm 10.1, -O3; same source shape as `repro.hip`, which was not
run on a GPU in this CPU-only batch). A 32-lane wave with y preset to `0xDEAD0000 + lane`; `permlane16` reverses each
row of 16, `permlanex16` reads lane `l ^ 16`. Five mask shapes per permute. "Lanes with a switched-off partner" are
active lanes whose source lane is off; the table counts those lanes that did not receive the partner's value
(they received the partner register's old `y` instead).

| Permute (fetch-inactive on) | Mask shape | Lanes with a switched-off partner | Wrong, source sunk | Wrong, source pinned |
|---|---|---:|---:|---:|
| `permlane16` | lanes 0-15 | 0 | n/a | n/a |
| `permlane16` | lanes 16-31 | 0 | n/a | n/a |
| `permlane16` | odd lanes | 16 | 16 of 16 | 0 of 16 |
| `permlane16` | every 4th lane | 8 | 8 of 8 | 0 of 8 |
| `permlane16` | data-dependent (host-chosen) | 7 | 7 of 7 | 0 of 7 |
| `permlanex16` | lanes 0-15 | 16 | 16 of 16 | 0 of 16 |
| `permlanex16` | lanes 16-31 | 16 | 16 of 16 | 0 of 16 |
| `permlanex16` | odd lanes | 0 | n/a | n/a |
| `permlanex16` | every 4th lane | 0 | n/a | n/a |
| `permlanex16` | data-dependent (host-chosen) | 13 | 13 of 13 | 0 of 13 |

So 3 of 5 mask shapes per permute have affected lanes, and all of those lanes are wrong; lanes whose partner is on are
right in every shape, and switched-off lanes are never written. With fetch-inactive off, a lane whose partner is off
keeps its own old value (not a bug).

Optimisation levels (ROCm 10.1, same kernels): at -O1, -O2, -Os and -O3 the pinned form is 100 % right. At -O0 the pin does not help: with the pin, 0 of 7 to 16 lanes with a switched-off partner get its value in all
6 shapes, because -O0 keeps the value in memory and only the active lanes reload it right before the permute (read in
one probe's listing, INFERRED for this kernel). ROCm 10.2 was not run on the card for this kernel.

These ROCm 10.1 hardware runs used LACT profile "Testing" (stock core clock and voltage, 1258 MHz memory, 317 W cap with
a 1.2x regulator mod); correctness counts do not depend on the clock. gfx1200 was not run (no such card).

## Workaround

Define the permute's source in front of the branch and pin it, or do the permute outside the branch:

```cpp
unsigned v = X[l] * 3u + 1u;
asm volatile("" : "+v"(v));      // every lane defines v before the branch
if (l < n) y = __builtin_amdgcn_permlane16(y, v, sel0, sel1, true, false);
```

`good_pinned` shows `before_mask` in every listing of the matrix above. The pin does not work at -O0 (see above).

## Suggested fix direction

The choice is the maintainers'. The IR passes treat the load and the arithmetic as ordinary single-use values and move
them into the only block that uses them. For a user that reads other lanes' registers, moving the definition into a
region that not every lane executes changes which lanes define the value. Options:
1. Do not sink (or hoist back) an instruction into a block when its only user is a cross-lane intrinsic with
   fetch-inactive set and the block is divergent.
2. Document in the builtin description that, with fetch-inactive, the source must be defined by all lanes and the
   compiler gives no guarantee for values computed inside the branch (users should pin or hoist).
