# The exact 8B comparison: how far are llama.cpp's 8B FP8 and Q8_0 files from the exact FP8 weights?

Measured 2026-11-18 (UTC 2026-11-19 00:17 to 00:40) on the LACT profile "Default" (the owner's overclock: 374 W cap, core +150 MHz, -50 mV, memory maximum 1409 MHz); **memory clock 1408 MHz before and after every job** (`uclk_before`, `uclk_after` in each `.meta`), so wall-clock numbers here are not comparable with the 1258 MHz jobs of `llm-runtimes.md`. KL divergence does not depend on speed. The expectations were committed first (`llm-8b-exact-expectations.md`, never edited). Labels: MEASURED (a run file is named), READ, INFERRED. Run folder `runs/20261119-llm8x/` (git-ignored); the 20 ms thermal guard (`llm-runtimes.md`, "Thermal guard") watched every job.

## Plain summary

0. **What this reference is, and is not.** The 8B reference is the FP8 checkpoint's own weights converted exactly (every FP8 value times its scale), **not Meta's original 16-bit 8B** (that file is not on disk). So the 8B numbers below measure how far each llama.cpp file is from the exact FP8 weights. That is a different question from round 4's 3B rows (3.7e-3 for the FP8 files, 4.3e-3 for Q8_0), which measure the distance from Meta's 16-bit weights; the two sets of numbers must not be set side by side as one measure. How far the 8B FP8 checkpoint itself is from Meta's 16-bit 8B was not measured. The reference run itself ran 22 of the 32 layers on the CPU, in F32 and F16 weights (see "Run 1 and run 2").
1. **Relative to the FP8 checkpoint's own weights, llama.cpp's FP8 route is practically exact on the 8B; the file the round 4 speed and quality rows used is not, because of its output matrix.** Against the exact FP8 weights (every FP8 value times its scale, stored without rounding), the plain FP8 file (`llama31-8b-auto`, unmodified build) has a mean KL divergence of **5e-6** (round 2's figure against an F16 file was also 5e-6). The `outq8` FP8 file (the same weights, but its output matrix stored as Q8_0) is **8.1e-5** (unmodified build) and **8.2e-5** (patched build): 16 times more. The two files differ in `output.weight` only (BF16 against Q8_0; all 740 tensors of both compared byte for byte by the reviewer, `auto-vs-outq8.txt` in the run folder).
2. **Q8_0 is 5.2e-4**, 6 times the `outq8` FP8 file and about 100 times the plain FP8 file. The patched and the unmodified build are the same within noise.
3. The reference needed the owner's one 16 GB job and one extra step: the first run of it was stopped at 96 C (the new guard worked), the second ran 10.6 minutes without heat trouble. the web browser was closed first (MemAvailable rose by 7,295,756 kB, about 7 GiB). The reference GGUF and the logits are deleted; sizes and sha256 are below.

## What it means

- (MEASURED) The exact-weights check of round 2's 3B (FP8 route 3e-6) now holds for the 8B too: the FP8 route itself (weights as FP8 times scale, FP16 activations) differs from the exact FP8 weights by 5e-6 (route plus the rounding of the reference's own CPU path, see "Run 1 and run 2"), and round 2's F16 reference was a good stand-in for it (5e-6 there as well). This says nothing about how far the FP8 checkpoint is from Meta's 16-bit 8B. Q8_0 is 5.2e-4 here against 6.1e-4 in round 2 (50 chunks of the same text, F16 reference); the difference is the chunk count and the reference, not a change in the model (8 chunks: standard error 1.8e-5, so the numbers are not the same sample).
- (MEASURED, with the control) The `outq8` file's output matrix in Q8_0 costs 8e-5 on its own, 16 times the whole FP8 route. Any quality comparison that uses `llama31-8b-fp8-outq8` (the files of round 4's speed rows and of its 3B and 8B quality rows) measures the output matrix quantisation as much as the FP8 weights. That 8e-5 is small against the 3B's 3.7e-3 distance from Meta's weights, so round 4's conclusion (the FP8 checkpoint's weights carry the error, not the route) stands. The Q8_0 file is 6 times further away than that file.
- (INFERRED) The 8B row of `llm-runtimes.md` R5 (perplexities 7.4439 to 7.4752 over 4 chunks) can now be read against the 8B exact reference, which it could not before; its numbers are unchanged.
